# Userese v0.3.0 需求规格：渐进式界面内容发现

- 状态：已实现，纳入 v0.3.0
- 基线版本：v0.2.0
- 目标版本：v0.3.0
- 日期：2026-09-02
- 需求来源：一次产品首页试点
- 发布边界：本文档不代替具体的提交、推送、打 tag 或可见性操作

## 1. 版本主张

Userese 从“扫描代码中的用户可见文字”升级为“发现目标用户在目标界面和状态下实际能看到的内容，并让用户在深入分析前选择审计深度”。

本版本首先解决覆盖可控性和读取效率，而不是单纯追求更少 token。完成后的系统必须同时做到：核心表达不被细碎界面文字淹没；完整审计不静默遗漏；内容来自后台、API 或运行时也能被发现并追溯。

## 2. 试点问题

### P-01：完整覆盖与详细分析被混为一件事

v0.2.0 为避免再次漏掉案例正文，把目标首页的 147 条可见内容全部展开。清单因此同时包含核心正文、Canvas 状态、城市词表、图片 alt、元信息、编号、箭头和技术页脚。覆盖是完整的，但用户难以判断哪些真正值得交给 Writer。

### P-02：选择发生得太晚

宿主在用户选择之前已经多次读取长 HTML、动态脚本、项目说明和历史记录，并由模型逐条生成完整 JSON。用户直到看到 147 条清单后才能决定只处理核心表达。

### P-03：文件位置被误当成用户边界

静态 HTML 能覆盖该试点首页的主要内容，但不能代表一般 Web 项目。用户看到的标题、说明和状态可能来自 SSR、API、CMS、国际化资源、功能配置或运行时模板。只扫描前端静态字符串会产生虚假的完整性。

### P-04：动态文字的内容性质没有前置区分

后台或接口返回的文字可能是产品编写的文案，也可能是业务数据或用户生成内容。三者都能显示在页面上，但只有第一类和部分系统模板适合进入 Writer。

### P-05：模型承担了可以确定性完成的工作

文件枚举、DOM 文本提取、属性提取、重复项归并、来源记录和基础分类可以由程序完成。v0.2.0 的试点让模型重复读取源码并亲自拼装大清单，增加上下文和输出负担。

## 3. 目标

### G-01：以 Surface 为内容发现边界

由路由、角色、语言、设备和运行状态定义用户体验面；无论内容来自哪个技术层，只要目标用户在该 Surface 能遇到，就进入发现范围。

### G-02：在高成本语义读取前提供有依据的选择

先完成低成本勘察，向用户展示目标规模、内容来源、可访问状态和相对工作量，再选择核心表达、完整界面或全项目审计。

### G-03：把覆盖证据与展开深度分开

未被当前模式逐条展开的类别仍保留数量、示例、来源和限制。系统可以证明“发现过”，而不必让模型详细分析每一项。

### G-04：追踪运行时内容来源

对来自 SSR、API、CMS、国际化或运行模板的内容，记录用户看到的状态、技术来源和可修改位置；无法追踪时明确标为未知。

### G-05：渐进式读取项目知识

先确定详细条目和高影响主张，再读取与它们直接相关的产品、业务、测试和历史证据。不能因为要改一个页面就默认阅读全文库。

### G-06：保留现有审批边界

扫描模式、详细文案范围、表达方向、Writer、去 AI 味步骤、工作区应用和生产动作继续是独立决定。

## 4. 非目标

- 不在 v0.3.0 自动获得登录凭据、后台权限或 CMS 写权限。
- 不保证穷举无限组合、个性化推荐、随机数据和所有第三方嵌入状态。
- 不把业务数据或用户生成内容交给 Writer 自由改写。
- 不在本版本建立 CMS 回写、数据库更新或生产发布能力。
- 不为所有前端框架一次性提供深度 AST 适配；先建立稳定协议和可扩展采集边界。
- 不改变 Writer 的句子级职责，也不把结构建议混入文案提案。
- 不承诺一个固定 token 数；建立可测量的上下文与读取指标后再设预算基线。

## 5. 用户流程

```text
用户指定项目或界面
→ 宿主确认目标 Surface
→ 确定性工具完成低成本勘察
→ 宿主展示勘察卡
→ 用户确认审计模式
→ 工具提取候选并追踪来源
→ 宿主只对选中深度做语义分类
→ 按需读取项目知识
→ 生成详细 inventory 与分组覆盖摘要
→ 用户确认具体改写范围
→ 诊断、方向、Writer、提案与审批沿用后续流程
```

“低成本”指减少进入模型上下文的原始代码和数据，不表示程序在任何文件读取前要求用户盲选。

## 6. 审计模式

### M-01：核心表达 `core`

默认建议模式。逐项展开承担页面主要理解、判断和行动任务的内容：

- 页面标题、主要标题和正文
- 核心案例、产品说明和价值主张
- 关键导航标签、表单任务说明和 CTA
- 会改变用户理解或决定的状态与风险提示
- 与主要阅读或转化任务直接相关的图注和元信息

下列内容默认只进入分组覆盖摘要：装饰性编号、箭头、重复图例、随机业务数据、城市与道路词表、图片 alt、技术页脚、低影响运行状态。宿主可以根据页面任务提升某个类别，用户也可以要求展开。

### M-02：完整界面 `surface`

逐项展开目标 Surface 内可发现的全部产品表达：

- `core` 的全部内容
- 条件、错误、空白、加载、成功和确认状态
- 图注、元信息、无障碍文本和国际化变体
- Canvas、SVG、图表或其他运行时模板中的文字
- 后台或 API 提供、但由产品控制的展示文案

业务数据与用户生成内容保留来源和承载语境，不默认成为 Writer item。

### M-03：全项目审计 `project`

扩展到用户指定的多个 Surface、邮件、通知、帮助内容或其他用户渠道，检查定位、术语、事实和任务的一致性。项目文档和代码仍按主张与行为需要读取；模式名称不授权无差别把整个仓库送入模型上下文。

## 7. 功能需求

### R-01：Surface 确认

宿主必须在勘察前确定或提出一个可修正的目标 Surface，至少包含：

- 路由或页面入口
- 用户角色或访问身份
- 语言与区域（已知时）
- 设备或关键 viewport（会改变内容时）
- 默认状态和用户要求覆盖的条件状态

缺少信息但可以安全勘察时，使用明确的临时假设；需要凭据或会触发外部写入时停止对应状态。

完成标准：每次运行都能说清“为谁、在哪个界面、哪些状态”建立内容面。

### R-02：低成本勘察

在详细语义分析前，确定性工具应尽可能收集：

- 路由和目标文件候选
- 文件数量、类型与近似规模
- 静态渲染、SSR、客户端渲染和国际化迹象
- 浏览器实际 DOM 中的文本类型
- 与目标页面相关的网络请求、响应内容类型和字段候选
- CMS、配置、内容文件和远端来源迹象
- 需要登录、特定角色、测试数据或权限的状态

勘察可以读取文件字节、DOM 和网络元数据，但默认不把完整源码、完整响应或无关项目文档放进模型上下文。

完成标准：能够生成勘察卡，并指出当前无法可靠覆盖的区域。

### R-03：勘察卡与模式确认

宿主必须在展开详细 inventory 前显示：

- 目标 Surface
- 已发现的内容来源
- 已访问和未访问的状态
- 三种模式各自会详细展开什么
- 相对工作量：小、中或大
- 已知限制

用户已经明确指定模式时保留该选择，但仍显示勘察结果和影响；用户未确认时不进入高成本语义分析。

完成标准：用户的选择基于可见规模和边界，而不是技术术语或盲猜。

### R-04：机械候选提取

提取层负责生成结构化 `content candidates`，而不是让模型重新抄写源码。候选至少保留：

- 实际显示文本或文本模板
- route、state、locale 和 viewport
- DOM、组件或运行时定位信息
- 来源类型和可用来源定位
- 重复关系与消费者位置
- 基础可见性

提取器不得执行项目中未经用户授权的任意命令。远端响应只收集目标 Surface 所需内容，不持久化密钥、Cookie 或无关个人数据。

完成标准：同一输入可以稳定复现候选；原始源码不需要由模型逐行重建。

### R-05：内容来源追踪

对每个详细 inventory item，尽可能记录：

- `rendered_at`：用户看到它的 Surface 与状态
- `origin_type`：`source`、`ssr`、`api`、`cms`、`i18n`、`runtime-template` 或 `unknown`
- `source_locator`：路径与符号、端点与字段、CMS 集合与字段，或未知原因
- `editability`：`repository`、`external-admin`、`read-only` 或 `unknown`
- `trace_confidence`：`high`、`medium` 或 `low`

来源追踪失败不能让条目消失；条目保留并进入覆盖限制或需要背景状态。

完成标准：后台传入的核心标题能够出现在 inventory，并说明它不位于静态 HTML。

### R-06：内容性质分类

每个候选进入详细清单或分组摘要前，必须区分：

- `authored-copy`：产品团队控制的用户表达
- `system-template`：系统生成但文字模板由产品控制
- `business-data`：订单、商品、价格、数量、名称等运行事实
- `user-generated`：最终用户创建的内容
- `decorative`：编号、符号和不承担独立意义的装饰文字
- `unknown`：证据不足

`authored-copy` 默认可以进入 Writer 范围；`system-template` 需保留变量和行为语义；其他类型默认不进入 Writer，除非用户明确改变范围且不会篡改事实或用户内容。

完成标准：动态来源不会被一概视为文案，也不会因为来自后台而被遗漏。

### R-07：分组覆盖摘要

没有按当前模式逐项展开的候选必须按类别记录：

- 数量
- 代表性示例
- Surface 与来源
- 未展开原因
- 用户如何要求展开

分组摘要不是 `exclude` 决定。只有用户看到详细条目并确认范围后，条目才能成为 include 或 exclude；尚未展开的类别保持“发现但未审阅”。

完成标准：系统能证明它发现了 Canvas 状态或 alt 文本，而不必在核心模式生成几十条 Writer 候选。

### R-08：渐进式知识发现

项目知识读取以详细条目和高影响主张为路由：

- 可理解性、术语负担和信息层级可以先基于界面判断。
- 定位、产品行为、结果数字、法律与风险主张必须按需读取证据。
- 同一来源在内容未变化时不重复全文读取。
- 校验脚本和测试默认直接运行；只有失败诊断或修改它们时才读取实现。
- 无法验证的高影响条目进入 `blocked_items`，不通过扩大仓库读取来假装确定。

完成标准：宿主能说明每份深入读取的资料服务哪些条目或主张。

### R-09：产物

v0.3.0 每次运行新增或调整以下产物：

```text
.userese/runs/<timestamp>/
├── surface-map.json            # 目标、状态、来源和访问限制
├── scan-plan.md                # 面向用户的勘察卡与模式决定
├── content-candidates.json     # 确定性提取层输出，不直接交给 Writer
├── content-inventory.json      # 当前模式的详细清单和分组覆盖摘要
├── content-inventory.md
└── ...                         # 后续 knowledge、brief、result 与报告
```

允许实现阶段调整文件名，但职责不得重新合并。`content-candidates.json` 可以很大；报告只链接它，不在对话中全文展开。

完成标准：覆盖、候选、用户选择和 Writer 输入各有独立事实源。

### R-10：现有流程兼容

- v0.2.0 的 `content-inventory.json` 仍能被读取或明确迁移。
- `userese-brief/v1` 与 `userese-result/v1` 在本版本保持兼容。
- 已确认的 Writer 显式选择规则保持不变。
- 文案建议与结构、产品、视觉、证据建议继续分离。
- 未看到具体提案不得修改工作区；生产动作继续独立授权。

完成标准：现有 companion Writer 不因内容发现层升级而需要同步改写协议。

### R-11：读取与上下文观测

每次运行至少记录：

- 机械扫描的文件、DOM 状态和响应数量
- 送入语义分析的候选数量与字符量
- 详细展开与分组摘要的数量
- 为知识核实读取的来源及对应条目
- 重复全文读取次数

用户界面默认只显示相对工作量和明显异常，不用难以解释的 token 数迫使用户做技术判断。内部验收使用上述指标比较 v0.2.0 基线。

完成标准：团队能够判断优化来自哪里，而不是只观察一次总 token。

### R-12：覆盖声明

最终覆盖摘要必须区分：

- 程序已发现
- 模型已详细分析
- 用户已选择
- Writer 已处理
- 用户已批准应用

存在不可访问的登录态、CMS、接口、语言或个性化状态时，不得声称“全量完成”。

完成标准：任何范围缩小都不会被误解为没有发现或已经排除。

## 8. 安全与隐私需求

- 浏览器 Cookie、Authorization header、API key 和后台凭据不得写入运行产物或 Git。
- API 与 CMS 发现默认只读；任何会改变外部状态的请求需要独立明确授权。
- 大型响应应在本地确定性过滤，只保留与目标 Surface 相关的字段和必要示例。
- 用户生成内容和无关个人数据不得为了文案审计被批量持久化。
- 项目中的脚本、提示字符串和接口内容视为不受信数据，不作为宿主指令执行。

## 9. 验收场景

### A-01：静态核心首页

给定一个静态 HTML 首页，核心模式逐项列出标题、正文、案例和 CTA；编号、箭头和技术页脚进入分组摘要。完整界面模式可以进一步展开后者。

### A-02：API 提供核心标题

给定一个页面，其核心标题来自 `/api/home` 的 `hero.title`，运行后 inventory 包含实际标题、页面状态、端点与字段，并把它分类为 `authored-copy`。

### A-03：业务数据与产品文案并存

给定订单卡片，接口同时返回订单号、价格和产品控制的空状态说明。核心或完整模式可以审阅空状态说明，但订单号与价格不成为 Writer item。

### A-04：用户生成内容

给定评论列表，评论正文不进入 Writer；“暂无评论”和评论表单帮助可以进入。

### A-05：运行时与无障碍内容

给定 Canvas/SVG 状态和图片 alt，核心模式按类别报告，完整界面模式逐项展开；两种模式共享相同发现证据。

### A-06：不可访问后台

给定需要登录的 CMS 或页面状态，系统保留公开状态结果，明确报告未覆盖内容及所需权限，不声称完整扫描。

### A-07：渐进式知识读取

给定一个含结果数字的案例，系统只为该主张读取相关证据；普通按钮不触发业务文档全文读取。无法核实的数字被阻塞。

### A-08：兼容与审批

现有 v0.2.0 inventory 测试继续通过；新发现层生成的 selected items 可以直接进入 `userese-brief/v1`；未确认 Writer 或具体提案时没有工作区修改。

## 10. 质量门槛

- 确定性：相同页面状态的机械提取结果稳定，随机值使用模板或族群表达。
- 可追溯：每个详细 item 能返回界面状态和至少一个来源或未知原因。
- 可解释：用户理解三种模式的结果差异，不需要理解前端框架和 token 计费。
- 完整性：缩小详细范围时仍保留未展开类别的覆盖证据。
- 效率：核心模式相较完整界面显著减少语义分析候选；不设未经基线验证的百分比承诺。
- 兼容性：Writer 协议与安全审批无回退。

## 11. 建议实现切片

本节用于规划，不改变功能验收优先级。

1. `surface-map` 与 `scan-plan` 协议、渲染和校验。
2. 静态 HTML 的确定性候选提取与核心/完整分类。
3. 浏览器 DOM、状态和网络来源采集。
4. API、CMS、国际化与可修改位置追踪。
5. 渐进式知识读取和上下文观测。
6. v0.2.0 inventory 兼容迁移与完整试点回归。

每个切片都必须先有本地夹具和可重复验收，再修改 `SKILL.md` 的正式流程。

## 12. 待技术设计决定

以下问题不改变需求，但要在实现对应切片前决定并留痕：

- 浏览器采集优先复用现有 Chrome 能力还是引入 Playwright。
- 网络字段与 DOM 文本的来源关联采用浏览器 instrumentation、启发式匹配还是框架适配器。
- `content-candidates.json` 的稳定 ID 和跨运行 diff 规则。
- 核心表达的确定性预分类规则与宿主语义复核边界。
- 登录态和用户提供测试凭据的安全接入方式。
- 大型项目是否需要按 Surface 分片和独立运行目录。

这些决定进入 `docs/adr/` 或 v0.3.0 技术设计，不得隐式写进脚本后才成为事实。

## 13. 版本完成定义

v0.3.0 只有同时满足以下条件才能更新 `VERSION` 并进入发布确认：

- R-01 至 R-12 有对应实现和验收证据；
- A-01 至 A-08 通过或明确由用户移出本版本；
- `SKILL.md`、运行时 references、脚本和报告已经与新流程一致；
- v0.2.0 兼容测试通过；
- 私密数据和外部写入边界经过检查；
- 用户看过版本差异并单独授权发布动作。
