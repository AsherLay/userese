# Userese v0.3.0 设计规范

## 继承与范围

继承 v0.2.0 的提案优先、安全审批和 Writer 分工。本版本只重新设计“深入读取之前如何建立界面内容面，以及如何让用户选择审计深度”；后续诊断、Writer、提案和落地边界继续保持。

## 一次运行的阅读顺序

```text
目标界面
→ 低成本勘察结果
→ 可覆盖与不可覆盖的状态
→ 三种审计模式及影响
→ 用户选择
→ 详细清单
→ 后续诊断与写作
```

用户不在没有信息时盲选，也不必等系统完整理解整个项目后才选择。勘察允许程序读取文件、DOM 和网络元数据，但模型只接收形成选择所需的摘要。

## 勘察卡

写入详细清单前，宿主用一段紧凑信息说明：

- 目标路由、角色、语言、设备和已知状态；
- 发现的静态、运行时、API、CMS、国际化等内容来源；
- 需要登录、测试数据或外部权限的状态；
- 每种审计模式预计会展开的内容类别和相对工作量；
- 当前无法保证的覆盖。

使用“小 / 中 / 大”表达相对工作量，不展示无法可靠预测的精确 token。

## 三种审计模式

### 核心表达（默认建议）

详细处理承担主要理解、判断和行动任务的标题、正文、案例、说明、关键标签和 CTA。元信息、无障碍、动态图和装饰元素只按类别报告数量与示例，用户可随时展开。

### 完整界面

逐项处理目标 Surface 内所有可发现的产品表达，包括条件状态、元信息、无障碍、图注、运行时模板和动态控件。实时业务数据与用户生成内容仍只记录边界，不交给 Writer 自由改写。

### 全项目审计

扩展到多个 Surface、渠道和长期内容来源，检查定位、术语、事实和用户任务的一致性。它不等于无差别读取全部仓库文件；知识来源仍按内容主张逐步展开。

## 分类与来源表达

每个详细条目至少让用户分辨：

- 它在什么界面和状态出现；
- 它是产品文案、运行模板、业务数据、用户内容、装饰或未知；
- 它来自源码、SSR、API、CMS、国际化资源还是未知位置；
- 它能在仓库、外部后台修改，还是目前只读或未知。

来源技术细节进入清单和 JSON；对话优先说用户在哪里看到、为什么值得审阅。

## 覆盖与范围

“已发现但未展开”必须按类别显示数量、示例和来源，避免把简洁误写成没有发现。详细条目仍全部保持 `pending`，直到用户确认本轮改写范围。

## 错误与恢复

无法访问登录态、CMS、接口或个性化状态时，先说明未覆盖什么以及当前结果仍包含什么，再说明需要的权限、样本或导出文件。不得用“全量扫描完成”描述存在关键不可访问状态的结果。

## 设计验收证据

- 静态 HTML、API 驱动页面、运行时生成内容和不可访问状态的本地夹具。
- 核心表达与完整界面对同一页面产生不同详细清单，但共享同一覆盖摘要。
- 对话中能清楚区分“程序已发现”“模型已分析”“用户已选择”和“Writer 已改写”。
